# SynthAudit-Bench Benchmark Release Checklist and Governance

**Benchmark version to release:** 1.0.0
**Software (frozen):** synthaudit-bench 0.0.1 (archived v1.0.0)
**Binds to:** specification Section 6.1.6 (validation), Section 12 (governance and SemVer), and the frozen `release.yml` automation.

> Scope note. This document defines the release, versioning, update, deprecation, and governance policy, and the checklist that gates the first benchmark release. It tags nothing; it is the gate the future release must pass.

---

## 1. The two version lines

SynthAudit-Bench versions two things independently:

- the **software** (the library that runs the benchmark), on Python SemVer, currently 0.0.1, frozen and archived as the v1.0.0 software tag;
- the **benchmark** (the corpus, ontology, gold, splits, and conformance set), on benchmark SemVer per specification Section 12.2.

This checklist releases the **benchmark** at 1.0.0. The software line does not move. The benchmark tag names the corpus release; the STO version and the schema versions it pins are recorded in the manifest.

## 2. Benchmark versioning policy (Section 12.2)

- **MAJOR** for any change that can alter a conforming system's score or break prior gold or outputs: changing the task, metrics, or matching; removing or redefining an STO class; removing datasets; reassigning the split; or changing gold or a tolerance.
- **MINOR** for additive changes that do not alter existing gold or scores: adding datasets, adding a domain term, adding clean negatives, or adding an STO class (which is itself a MINOR ontology change).
- **PATCH** for fixes that change neither gold nor scores: a metadata typo, an added citation, or a documentation correction.

The release automation blocks a tag whose declared bump disagrees with the changelog and the diff class.

## 3. Release process

The release runs through the frozen `release.yml` automation on a tag, and any failure blocks the tag:

1. **Validate the corpus** against Section 6.1.6: schema validation of every record, referential integrity, hash integrity, split integrity, and the license gate.
2. **Run compliance** (CS-1..CS-7) against the reference and baseline detectors on the conformance set.
3. **Build the bundle** from `registry/`, `sto/`, `schemas/`, generated tables, report cards, `conformance/`, and `MANIFEST.json`, **excluding held-out gold**.
4. **Export Croissant** records per dataset, with the report card under the namespaced key.
5. **Build the docs** with `mkdocs --strict`.
6. **Deposit to Zenodo** on an explicit, tokened, opt-in step, recording the DOI back into `CITATION.cff` and the manifest.
7. **Attach artifacts** and hash-stamp the release. Releases are immutable.

## 4. Update policy

- New datasets are added as new instances with new ids; they never mutate existing instances. Adding datasets is MINOR.
- The census frame may be re-enumerated for a later version with a new documented enumeration and retrieval date; the prior frame stays reproducible.
- The held-out partition may be regenerated by re-seeding the planted and controlled generators; the public split assignment for a released version is fixed.
- Tolerances and gold are frozen within a version; changing either is MAJOR.

## 5. Deprecation policy

- An instance is corrected by minting a new instance and writing a tombstone `{id, deprecated: true, reason, replaced_by, since_version}`. The old bytes remain available so prior results reproduce.
- A dataset is retired by tombstoning it; removal from the scored set is MAJOR.
- An STO class is never removed or redefined incompatibly; a deprecated class is retained with a replacement pointer and the version of deprecation. STO changes are ontology-versioned separately and pinned per release.

## 6. Governance

- **Maintainers** steward the specification, ontology, corpora, gold, and compliance suite, and approve releases.
- **Contributors** propose datasets, classes, or corrections through the change process: a proposal that specifies every required record or register field, a justification, and, for a new class, a gold type and a non-overlap note.
- **Adjudicators** are independent for the adjudicated gold and follow `ANNOTATION-MANUAL.md`; no maintainer uses a detector as an oracle.
- **Change process.** Proposals are reviewed, assigned a SemVer impact, and either accepted into the next version or deferred. All accepted changes are recorded in the benchmark `CHANGELOG.md` with their SemVer class.
- **Conformance claims** cite the benchmark version and the compliance result hash; the maintainers do not certify systems, they publish the suite that systems certify against.

## 7. First benchmark release checklist (v1.0.0)

Everything below must be true before `synthaudit-bench-1.0.0` (the benchmark) is tagged. Each item names the document or gate that establishes it.

### 7.1 Controlled vocabularies and templates
- [ ] Domain vocabulary fixed and published (`CORPUS-PROTOCOL.md` Section 6.3, `templates/controlled-vocabularies.md`).
- [ ] Generator-family vocabulary confirmed against the frozen enum.
- [ ] Record, gold, manifest, tolerances, decision-log, and annotation-record templates validate against the frozen schemas.

### 7.2 Census corpus
- [ ] `corpus/census/frame.md` fixes the repository, query, retrieval date, enumeration script, and second-repository fallback.
- [ ] Enumeration reproduces from the script.
- [ ] Every include or exclude decision logged with a reason (`corpus/census/inclusion-exclusion.md`).
- [ ] Deduplication and pseudo-replication capping applied and documented.
- [ ] Target n reached or a documented shortfall with the contingency invoked.
- [ ] Every census record carries `frame_stratum: census`, `domain`, `generator_family`, `provenance_confidence`.

### 7.3 Evaluation corpus
- [ ] Planted, controlled, and adjudicated_real strata populated to their designed minimums (`corpus/evaluation/design.md`).
- [ ] Every one of the sixteen STO classes represented by multiple positives.
- [ ] Clean negatives present at the designed fraction; class balance matches the manifest design within tolerance.
- [ ] Diversity minimums met across generator family, domain, task, and size (`CORPUS-PROTOCOL.md` Section 4.2).
- [ ] Controlled roster pinned (at most five bases, at most seven generators) with seeds and tool versions recorded.

### 7.4 Gold
- [ ] Objective gold machine-verified on the released bytes for all thirteen objective classes, with recorded evidence.
- [ ] Adjudicated gold produced by two independent annotators under `ANNOTATION-MANUAL.md`, oracle-free.
- [ ] Inter-annotator agreement meets the thresholds (Cohen kappa at least 0.70 presence, at least 0.60 disposition) and is published.
- [ ] Unreconciled items marked `optional` or excluded; reconciliation logged.
- [ ] Every gold tuple validates against `gold-tuple.schema.json`.

### 7.5 Splits
- [ ] `evaluation/splits.json` assigns every evaluation dataset to `public-dev` or `held-out` by the documented seeded procedure.
- [ ] Held-out gold withheld; the public bundle excludes it.
- [ ] Leakage checks pass; no undisclosed shared base table crosses the split.
- [ ] Split integrity validated (Section 6.1.6).

### 7.6 Conformance set
- [ ] Fixtures cover every CS item: objective positives across all thirteen objective classes, adjudicated positives for A06/P01/D01, clean negatives, and at least one out-of-class artifact (`CONFORMANCE-PLAN.md`).
- [ ] `conformance/gold/` published; `conformance/tolerances.json` pinned to the v1.0 defaults.
- [ ] `conformance/expected/` frozen from the reference implementation and labeled as a cross-check (generated after fixtures exist).
- [ ] CS-1..CS-7 pass for the reference and baseline detectors.

### 7.7 Evaluation
- [ ] Baseline ladder pinned and registered (`EVALUATION-PROTOCOL.md`).
- [ ] Pipeline runs end to end on `public-dev`; metrics, breakdowns, and coverage produced.
- [ ] Run manifests recorded; `bench reproduce` passes on a fresh environment.

### 7.8 Provenance, licensing, and metadata
- [ ] Every dataset has source URLs, retrieval date, license with SPDX, and redistributability flags.
- [ ] Fetch stubs carry expected hashes; no forbidden redistribution.
- [ ] The reproducibility asymmetry is stated in `MANIFEST.json`.
- [ ] Per-dataset license texts included under `LICENSES/`.

### 7.9 Manifest and layout
- [ ] `MANIFEST.json` lists id, sha256, byte size, row and column counts, corpus, split, license, and source for every instance.
- [ ] The release follows the normative layout of specification Section 6.1.2.
- [ ] Every present file matches its manifest hash; every stub declares an expected hash.

### 7.10 Identity and citation
- [ ] `CITATION.cff` updated with the benchmark version and, once minted, the Zenodo DOI.
- [ ] Benchmark `CHANGELOG.md` records the v1.0.0 benchmark release and its SemVer class.
- [ ] The release is hash-stamped and immutable.

### 7.11 Final gate
- [ ] Specification Section 6.1.6 validation passes in full.
- [ ] `release.yml` completes with no failure.
- [ ] Held-out gold confirmed absent from the public bundle.
- [ ] Tag `synthaudit-bench-1.0.0` (benchmark) applied only after every box above is checked.

## 8. What Phase 3 delivers versus what the release requires

Phase 3 (this package) delivers Section 7.1 in full and the protocols, templates, and gates for Sections 7.2 through 7.11. The remaining boxes are checked during execution of the construction roadmap (Blueprint Section 4), which annotates datasets, establishes gold, and runs baselines. Those steps are deliberately out of scope here; the stop condition forbids them.
